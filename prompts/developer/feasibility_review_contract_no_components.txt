【输出文件】`stage_outputs/feasibility_review.json`

文件必须是且仅是一个合法 JSON 对象：

{
  "schema_version": "1.0",
  "decision": "accept | reject",
  "responsibility": "instance | algorithm_design | solving | null",
  "summary": "验收结论及主要依据",
  "evidence": [
    {
      "source": "具体文件及字段或代码位置",
      "finding": "该证据证明了什么"
    }
  ],
  "required_changes": ["责任阶段需要完成的具体修复"],
  "confidence": "low | medium | high",
  "infeasibility_proof": "实例不可行证明的类型、来源和适用范围；非 instance 时为空字符串",
  "remediation_handoff": {
    "requirement_ids": ["稳定的业务要求 ID，例如 vehicle_capacity"],
    "change_ids": ["稳定的修复动作 ID，例如 capacity_aggregation"],
    "problem_requirement": "problem.md/intake 中对应的业务硬约束",
    "observed_solution_behavior": "旧 solution 在业务语义上的失败表现",
    "responsibility_reason": "为什么属于目标阶段的职责",
    "required_changes": ["不依赖 checker 实现细节的语义修复动作"]
  }
}

字段规则：
- accept：responsibility 必须为 null，required_changes 必须为空数组，infeasibility_proof 必须为空字符串，remediation_handoff 必须为 null。
- reject：responsibility 必须且只能是 instance、algorithm_design、solving，evidence 至少一条。
- responsibility=instance：required_changes 必须为空数组，infeasibility_proof 必须非空，remediation_handoff 必须为 null；只有 solver_result.status=infeasible、结构化 solver_result.infeasibility_proof 完整，且证据表明同一个完整精确模型忠实覆盖全部硬约束时才允许使用。无候选终态不得归为 instance。
- responsibility=algorithm_design 或 solving：required_changes 至少一条，infeasibility_proof 必须为空字符串，remediation_handoff 必须提供。
- evidence、summary 和顶层 required_changes 属于 Core/Reviewer 私有审计信息，可以精确引用证据。
- remediation_handoff 是唯一会发给责任阶段的内容，只能使用 problem.md/intake 中的业务语义和旧 solution 的可观察行为。不得出现 checker、feasibility_result、feasibility_checker、代码行号、函数名、内部判定字段或如何迎合检查逻辑的描述。
- remediation_handoff.requirement_ids 与 change_ids 必须是稳定、简短的 lowercase_snake_case ID，供 Core 压缩早期历史；不得把证据或解释塞入 ID。它们只是标识，不构成任何判定依据；是否重复既往修复一律以 remediation_handoff.required_changes 的语义为准。
- 不得输出 contract、checker、schema、unknown、clarification 或其他责任。
- recommended_route 不属于当前契约；Reviewer 只输出责任，Core 会把 algorithm_design 和 solving 确定性路由到对应阶段。
- 归责 solving 必须指出当前实现相对 Algorithm Design 的一个具体偏差，且该偏差要求的修复动作必须与既往 remediation_handoff.required_changes 语义不同。若当前实现已落实既有 solving 修复、同一 runtime_timeout 或失败模式仍然出现，或者本轮要求的修复动作与既往实质相同，则必须归责 algorithm_design；不得以“尚不能证明 algorithm_design”为由默认归责 solving。判断是否重复只看 remediation_handoff.required_changes 的语义，不看 change_ids 字符串；换一个 change_id 写法但要求同一件事，仍属重复。压缩账本不含既往 required_changes 原文；历次裁决全文与 checker 结果在 feasibility_review_history.json（仅本阶段可读，责任阶段被隔离），连续判 solving 前必须读取它核对。单次 runtime_timeout 仍需结合当前实现判断，不得仅按状态机械归责；runtime_timeout 表示 Runtime 外部强制终止。time_limit 表示求解器正常返回时间限制：携带完整候选时必须检查候选，不适用重复 runtime_timeout 的机械升级规则；没有候选时再依据实际执行证据归责。
- 非证明型搜索多次无法产生完整可行候选且没有新的实现缺陷时，归责 algorithm_design。remediation_handoff 必须要求重新评估算法族、完整 formulation 和预算，并在规模与结构允许时评估一次带独立时限、覆盖全部硬约束的证明型精确求解；不得要求无条件使用精确法，也不得暗示精确求解的 time_limit、unknown 或未找到解能够证明实例不可行。
- algorithm_design 或 solver.py 出现分解策略、warm start、MIP start、备用算法或降级路线时必须 reject；设计中已有该内容时责任为 algorithm_design，实现自行加入时责任为 solving。

候选解路径必须先读取 feasibility_checker.py，再用一次独立的 shell 调用按其实际 CLI 执行它，使其对当前 input.json 和 solution.json 生成新的 feasibility_result.json；不得在同一命令中串联 solver、循环或其他程序。不得假设 --data-dir 或其他参数存在。若命令、参数、路径或结果文件处理失败，先自行诊断并重试；只有 shell 明确提示同一失败已重复 5 次时，停止重试并输出 reject，责任只能是 solving，且 remediation_handoff 不得包含 checker 细节。再读取 feasibility_result.json。无候选路径不得要求 solution.json、不得执行 checker，必须根据 status（runtime_timeout 表示 Runtime 外部强制终止；time_limit 表示求解器正常返回）、diagnosis、execution、solver.py、algorithm_design 和压缩账本拒绝并归责 algorithm_design 或 solving。若 solver_result.status=infeasible，则同样不执行 checker，改为核验结构化不可行证明。写入 verdict 后用 read_file 检查最终文件。不要修改任何其他文件。

--- BEGIN ENGLISH TRANSLATION (DOCUMENTATION ONLY; NOT LOADED AT RUNTIME) ---

[OUTPUT FILE] `stage_outputs/feasibility_review.json`

The file must contain exactly one valid JSON object:

{
  "schema_version": "1.0",
  "decision": "accept | reject",
  "responsibility": "instance | algorithm_design | solving | null",
  "summary": "Acceptance conclusion and primary basis",
  "evidence": [
    {
      "source": "Specific file and field or code location",
      "finding": "What this evidence proves"
    }
  ],
  "required_changes": ["Specific repairs that the responsible stage must complete"],
  "confidence": "low | medium | high",
  "infeasibility_proof": "Type, source, and scope of the instance-infeasibility proof; empty string when responsibility is not instance",
  "remediation_handoff": {
    "requirement_ids": ["Stable business-requirement ID, such as vehicle_capacity"],
    "change_ids": ["Stable repair-action ID, such as capacity_aggregation"],
    "problem_requirement": "Corresponding business hard constraint in problem.md/intake",
    "observed_solution_behavior": "Business-semantic failure exhibited by the old solution",
    "responsibility_reason": "Why this belongs to the target stage's responsibility",
    "required_changes": ["Semantic repair actions independent of checker implementation details"]
  }
}

Field rules:
- accept: responsibility must be null, required_changes must be an empty array, infeasibility_proof must be an empty string, and remediation_handoff must be null.
- reject: responsibility must be exactly one of instance, algorithm_design, or solving, with at least one item in evidence.
- responsibility=instance: required_changes must be an empty array, infeasibility_proof must be nonempty, and remediation_handoff must be null. It is permitted only when solver_result.status=infeasible, the structured solver_result.infeasibility_proof is complete, and evidence shows that the same complete exact model faithfully covers all hard constraints. A no-candidate final state must not be assigned to instance.
- responsibility=algorithm_design or solving: required_changes contains at least one item, infeasibility_proof must be an empty string, and remediation_handoff must be provided.
- evidence, summary, and top-level required_changes are private Core/Reviewer audit information and may cite evidence precisely.
- remediation_handoff is the only content sent to the responsible stage and may use only business semantics from problem.md/intake and observable behavior of the old solution. It must not mention the checker, feasibility_result, feasibility_checker, code line numbers, function names, internal adjudication fields, or how to cater to checking logic.
- remediation_handoff.requirement_ids and change_ids must be stable, concise lowercase_snake_case IDs for Core to compress earlier history; do not put evidence or explanations into IDs. They are identifiers only and provide no basis for adjudication. Whether a repair repeats a previous repair is determined solely by the semantics of remediation_handoff.required_changes.
- Do not output contract, checker, schema, unknown, clarification, or another responsibility.
- recommended_route is not part of the current contract. Reviewer outputs responsibility only; Core deterministically routes algorithm_design and solving to the corresponding stage.
- Assigning solving requires identifying one concrete deviation of the current implementation from Algorithm Design, and its required repair action must be semantically different from previous remediation_handoff.required_changes. If the current implementation has applied existing solving repairs and the same runtime_timeout or failure mode still occurs, or the requested repair is materially the same as a prior one, responsibility must be algorithm_design; do not assign solving by default because algorithm_design has "not yet been proven." Determine repetition from the semantics of remediation_handoff.required_changes, not the change_ids strings. Rewriting the same request with another change_id still counts as repetition. The compressed ledger does not contain earlier required_changes text; full previous verdicts and checker results are in feasibility_review_history.json (readable only in this stage and isolated from responsible stages), and you must read it before assigning solving consecutively. A single runtime_timeout still requires assessment against the current implementation and must not be assigned mechanically from status alone. runtime_timeout means forced external termination by Runtime. time_limit means the solver returned normally at its time limit: when it carries a complete candidate, the candidate must be checked and the mechanical repeated-runtime_timeout escalation rule does not apply; when it has no candidate, assign responsibility from actual execution evidence.
- When non-proof search repeatedly fails to produce a complete feasible candidate and there is no new implementation defect, assign algorithm_design. remediation_handoff must require reevaluation of the algorithm family, complete formulation, and budget, and, when scale and structure permit, evaluation of one proof-producing exact solve with an independent time limit covering all hard constraints. Do not unconditionally require an exact method, and do not imply that an exact solve's time_limit, unknown, or failure to find a solution can prove instance infeasibility.
- If algorithm_design or solver.py contains a decomposition strategy, warm start, MIP start, backup algorithm, or degraded route, it must be rejected; responsibility is algorithm_design if that content is already in the design, or solving if the implementation added it itself.

On the candidate path, first read feasibility_checker.py, then execute it according to its actual CLI in one independent shell call so it generates a fresh feasibility_result.json for the current input.json and solution.json; do not chain a solver, loop, or other program in the same command. Do not assume that --data-dir or another parameter exists. If command, parameter, path, or result-file handling fails, diagnose and retry. Stop retrying and output reject only when shell explicitly reports that the same failure has repeated five times; responsibility may only be solving, and remediation_handoff must not contain checker details. Then read feasibility_result.json. The no-candidate path must not require solution.json or execute the checker; it must reject and assign algorithm_design or solving based on status (runtime_timeout means forced external termination by Runtime; time_limit means normal return by the solver), diagnosis, execution, solver.py, algorithm_design, and the compressed ledger. If solver_result.status=infeasible, likewise do not execute the checker; instead verify the structured infeasibility proof. After writing the verdict, use read_file to inspect the final file. Do not modify any other file.
