【输出文件】`stage_outputs/problem_contract.json`

你必须同时写入以下 workspace 文件：
- `solution_schema.json`
- `feasibility_checker.py`
- `stage_outputs/problem_contract.json`

【两种执行模式】

- 若没有提供独立审计反馈，执行首次设计：根据事实来源生成完整的三个 contract 文件。
- 若提供了“当前独立审计反馈”，执行审计退回修订：先完整读取现有三个 contract 文件，再以现有版本为基线进行增量修改。
- 审计退回时，逐条落实所有 `blocking` finding 的 `required_change`；逐条判断 `warning`，不得静默忽略。
- 只修改解决 finding 所必需的内容，保留原契约中仍然正确的设计，不得无理由更换 solution 语义或重写无关部分。
- 即使 finding 只涉及一个文件，完成后也必须重新验收三个文件的业务语义与跨文件一致性。
- 不得修改 `problem.md`、`stage_outputs/intake.json`、`data/` 或审计结果文件，也不得开始算法设计。
- 当前修订成功写入后，旧审计意见不再代表当前版本；不要把更早的 contract 或 audit 历史带入输出。

【schema 设计要求】
- `solution_schema.json` 必须是 JSON Schema Draft 2020-12 的合法 JSON 对象。
- 本次运行不提供输入结构契约：既没有 input_schema.json，也没有输入结构说明。规范化 input.json 的字段、类型和维度必须由你自行读取 `data/` 确定。
- solution schema 描述 problem-level semantic solution，不能暴露 x[i,j]、y[k,t]、interval_var、route_arc_binary 等算法级决策变量。
- schema 应包含足够字段让 checker 能判断硬约束、计算目标值或说明目标不可计算原因。

【feasibility_checker.py 要求】

【feasibility_checker 自检边界】
- feasibility_checker 必须依据公开的问题定义检查候选 solution，不得依赖 solver.py、algorithm_design 或其他未写入 contract 的外部产物。
- 自检必须使用字段完整、明确违反约束的人工负例；不得先寻找可行解，也不得使用不完整 solution 作为测试输入。
- 不得在真实规模数据上反复运行 feasibility_checker，以搜索、补全或重新求解不完整 solution 中缺失的组合安排。
- 若某项判定本身需要组合可行性检查，只能在自检所需的小规模人工负例上执行；本阶段不得把大规模补全式搜索作为调试路径。

必须暴露：

def check(input_data: dict, solution: dict, data_dir: str | Path = "data") -> dict

必须支持 CLI：

python feasibility_checker.py --input input.json --solution solution.json --data-dir data --output feasibility_result.json

上述命令是供后续阶段使用的 CLI 契约，不是本阶段的验收命令。`input.json`、`solution.json` 和 `feasibility_result.json` 在本阶段均尚未构造：只在 `stage_outputs/problem_contract.json` 中记录其未来文件名，绝不可创建、覆盖、要求其存在或以它们执行 CLI。

输出必须是 JSON 可序列化 dict，结构如下：

{
  "schema_valid": true,
  "feasible": false,
  "objective_value": null,
  "violations": [
    {
      "constraint": "vehicle_capacity",
      "message": "Vehicle 3 exceeds capacity by 12.5",
      "severity": "error"
    }
  ],
  "warnings": []
}

字段含义：
- schema_valid: input/solution 是否满足 schema；若 schema 校验失败，feasible 必须为 false。
- feasible: 所有硬约束是否满足。
- objective_value: 可从解和数据计算出的目标值；无法计算时为 null 并在 warnings 说明。
- violations: 每个硬约束或 schema 错误的结构化违反项。
- warnings: 不影响可行性的提示、软约束说明或目标计算注意事项。

【stage_outputs/problem_contract.json 格式】
推荐结构：

{
  "problem_family": "routing/scheduling/assignment/packing/network_flow/inventory/production_planning/facility_location/mixed_combinatorial/other",
  "message": "简短说明",
  "files": {
    "solution_schema": "solution_schema.json",
    "feasibility_checker": "feasibility_checker.py",
    "expected_input": "input.json",
    "expected_solution": "solution.json",
    "expected_feasibility_result": "feasibility_result.json"
  },
  "semantic_solution": {
    "primary_objects": ["业务解中的核心对象"],
    "required_fields": ["solution.json 必须包含的关键字段"],
    "algorithm_independence_notes": "为什么该格式不绑定具体算法"
  },
  "input_contract": {
    "required_entities": ["规范化 input.json 必须包含的实体"],
    "data_sources": ["data/ 中会被使用的文件或字段"],
    "normalization_notes": "solving 如何从 data/ 组装 input.json"
  },
  "checker_contract": {
    "entrypoint": "check(input_data, solution, data_dir='data')",
    "cli": "python feasibility_checker.py --input input.json --solution solution.json --data-dir data --output feasibility_result.json",
    "checks": ["会独立检查的硬约束和目标项"]
  },
  "assumptions": []
}

写完后必须自行验收：
- `solution_schema.json` 可被 json.load 读取。
- `feasibility_checker.py` Python 语法正确，并包含 check()。
- `stage_outputs/problem_contract.json` 是合法 JSON 对象。
- 本阶段自检只验证以上三个 contract 文件；不得因 `input.json`、`solution.json` 或 `feasibility_result.json` 尚不存在而报错。
