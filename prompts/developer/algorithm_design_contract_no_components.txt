验收规则：
- 多轮 pilot 或建模验证必须优先复用 Runtime 已预置的 `scratch/` 中的数据准备、索引映射、候选集合和模型骨架；不得自行创建其他临时根目录。每个阶段结束后 Runtime 清空 `scratch/` 内容并保留目录，因此脚本只保证在当前阶段内可复用。后续调用不得在无必要时重新解析全部数据、重建全部变量和约束。只有输入映射、变量定义或约束语义发生实质变化时，才重建受影响部分。
- 可复用脚本应将数据准备、模型构建、求解和结果检查分层，并使用独立参数/输出文件；不得依赖上一次进程的内存状态或 `/tmp` 中不可保证持续存在的脚本；临时产物不得冒充最终阶段输出。
- 如果设计本身已经包含多个彼此独立的方案、solver 或 pilot 验证，可以并行执行；不得因为并行而额外增加候选或改变选择范围。存在数据依赖或共享可变状态时必须串行。
- 主机有 16 个逻辑运算单元，单次 shell 调用的并发子进程/任务数不得超过 8；不得通过嵌套脚本或多层线程/进程池突破上限。
- 并行任务必须隔离输入、`scratch/<task-id>/` 子目录和输出，保留任务 ID、退出码、耗时、超时和关键指标；失败任务不得污染或阻断其他任务。不得重复运行同一个失败命令，也不得改变 solver_timeout_seconds 总预算。
- 若采用并行验证，最终方案必须记录既定验证任务集合、并发上限和汇总依据。
- 关键规模数字必须来自工具计算，无法可靠估算时填 null。
- package 发现必须先使用系统注入的一句话目录摘要完成初筛，不得通过逐个调用 get_algorithm_guide 遍历全部 package。
- 只有 shortlist 中需要认真比较或最终采用的 package 才读取完整 guide；写入 candidates 或 algorithm 的 package 必须已经读取 guide。
- status=experimental 或 not_benchmarked 不得描述为已验证高效。
- 启发式失败只能标记 unknown，不得证明原问题 infeasible。
- 最终 algorithm 不得使用分解策略、warm start 或 MIP start。不得设计备用算法或降级路线；选定算法失败或不可用时必须如实报告实际终态。
- Reviewer handoff 表明非证明型搜索多次未产生完整可行候选时，新设计不得仅原样延长或以不同随机种子重跑同一方法；必须重新评估算法族、完整 formulation 和预算。规模与结构允许时，至少在 candidates 或 algorithm 中评估一个带独立时限且覆盖全部硬约束的证明型精确方案；不适合时必须明确记录建模规模或预算障碍。精确方案的 time_limit、unknown 或未找到解不得描述为 infeasible 证明。
- package API、能力、版本和保证只能引用完整 guide。
- formulation 必须覆盖当前范围内全部硬约束，Big-M 和整数缩放必须可解释。
- 提交 solver 内的算法预算、转换、checker 和输出必须闭合于 SOLVER_TIMEOUT；算法设计阶段的 API/数据结构探针和方案比较不计入该 solver 预算。
