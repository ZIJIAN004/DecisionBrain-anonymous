【输出文件】`stage_outputs/feasibility_review.json`

文件必须是且仅是一个合法 JSON 对象：

{
  "schema_version": "1.0",
  "decision": "accept | reject",
  "responsibility": "instance | solving | null",
  "summary": "验收结论及主要依据",
  "evidence": [
    {"source": "具体文件及字段或代码位置", "finding": "该证据证明了什么"}
  ],
  "required_changes": ["Formulator 需要完成的具体修复"],
  "confidence": "low | medium | high",
  "infeasibility_proof": "实例不可行证明的类型、来源和适用范围；非 instance 时为空字符串",
  "remediation_handoff": {
    "requirement_ids": ["稳定的业务要求 ID"],
    "change_ids": ["稳定的修复动作 ID"],
    "problem_requirement": "problem.md/intake 中对应的业务硬约束",
    "observed_solution_behavior": "旧 solution 的业务失败表现",
    "responsibility_reason": "Formulator 完整模型的具体责任原因",
    "required_changes": ["不依赖 checker 实现细节的语义修复动作"]
  }
}

字段规则：
- accept：responsibility 为 null，required_changes 为空数组，infeasibility_proof 为空字符串，remediation_handoff 为 null。
- reject：responsibility 为 instance 或 solving，evidence 至少一条。
- instance：required_changes 为空数组，infeasibility_proof 非空，remediation_handoff 为 null；solver_result.status 必须为 infeasible，结构化证明完整，且代码与执行证据表明一个完整精确模型覆盖全部硬约束。
- solving：required_changes 至少一条，infeasibility_proof 为空字符串，remediation_handoff 必须提供。
- remediation_handoff 只写业务要求、旧 solution 可观察行为、责任原因和语义修复动作；不得包含 checker、feasibility_result、代码行号、函数名或内部判定字段。
- requirement_ids 与 change_ids 使用稳定、简短的 lowercase_snake_case。

候选解路径：
- 先读取 feasibility_checker.py，再按其实际 CLI 用 run_feasibility_checker 对当前 input.json 和 solution.json 执行一次，使其生成新的 feasibility_result.json。
- 不假设 checker 参数；执行或路径失败时诊断后重试。工具明确提示同一失败重复 5 次时，reject 并归 solving。
- feasibility_check_receipt.json 必须仍与当前 checker、input、solution 和 result 一致。
- feasibility_result.schema_valid=true 且 feasible=true 才可 accept。

无候选路径：
- 不要求 solution.json，不执行 checker。
- 审查 status、diagnosis、execution、solver.py、runtime_solver_outcome.json（如有）和修复历史。
- runtime_timeout、time_limit、unknown、no_solution_found 和 infeasible_or_unbounded 均须 reject，责任为 solving，并指出 Formulator 在完整模型、求解调用、状态处理或业务结果映射中需要修复的具体事项。

正式不可行路径：
- 不执行 checker。
- 核对 infeasibility_proof、solver.py、实际 execution、全部变量、全部硬约束和完整目标。
- 只有完整模型的可信 Gurobi INFEASIBLE 状态或证书可归 instance。

写入 verdict 后用 read_file 检查最终文件。不要修改其他文件。

[OUTPUT FILE] `stage_outputs/feasibility_review.json`

The file must contain exactly one valid JSON object:

{
  "schema_version": "1.0",
  "decision": "accept | reject",
  "responsibility": "instance | solving | null",
  "summary": "Acceptance conclusion and primary basis",
  "evidence": [
    {"source": "Specific file and field or code location", "finding": "What this evidence proves"}
  ],
  "required_changes": ["Specific repairs that the Formulator must complete"],
  "confidence": "low | medium | high",
  "infeasibility_proof": "Type, source, and scope of the instance-infeasibility proof; empty string when responsibility is not instance",
  "remediation_handoff": {
    "requirement_ids": ["Stable business-requirement ID"],
    "change_ids": ["Stable repair-action ID"],
    "problem_requirement": "Corresponding business hard constraint in problem.md/intake",
    "observed_solution_behavior": "Observable business failure in the old solution",
    "responsibility_reason": "Specific reason why the Formulator's complete model is responsible",
    "required_changes": ["Semantic repair actions independent of checker implementation details"]
  }
}

Field rules:
- accept: responsibility is null, required_changes is an empty array, infeasibility_proof is an empty string, and remediation_handoff is null.
- reject: responsibility is instance or solving, with at least one item in evidence.
- instance: required_changes is an empty array, infeasibility_proof is nonempty, and remediation_handoff is null; solver_result.status must be infeasible, the structured proof must be complete, and code and execution evidence must show that one complete and exact model covers all hard constraints.
- solving: required_changes contains at least one item, infeasibility_proof is an empty string, and remediation_handoff must be provided.
- remediation_handoff contains only business requirements, observable behavior of the old solution, the responsibility reason, and semantic repair actions; it must not contain the checker, feasibility_result, code line numbers, function names, or internal adjudication fields.
- requirement_ids and change_ids use stable, concise lowercase_snake_case.

Candidate-solution path:
- First read feasibility_checker.py, then use run_feasibility_checker according to its actual CLI to execute it once against the current input.json and solution.json, causing it to generate a fresh feasibility_result.json.
- Do not assume checker parameters; diagnose and retry execution or path failures. When the tool explicitly reports that the same failure has repeated five times, reject and assign responsibility to solving.
- feasibility_check_receipt.json must still agree with the current checker, input, solution, and result.
- You may accept only when feasibility_result.schema_valid=true and feasible=true.

No-candidate path:
- Do not require solution.json and do not execute the checker.
- Review status, diagnosis, execution, solver.py, runtime_solver_outcome.json (if present), and repair history.
- runtime_timeout, time_limit, unknown, no_solution_found, and infeasible_or_unbounded all require rejection with responsibility assigned to solving, identifying the specific item that the Formulator must repair in the complete model, solve invocation, status handling, or business-result mapping.

Formal-infeasibility path:
- Do not execute the checker.
- Verify infeasibility_proof, solver.py, actual execution, all variables, all hard constraints, and the complete objective.
- Responsibility may be assigned to instance only with a trustworthy Gurobi INFEASIBLE status or certificate from a complete model.

After writing the verdict, use read_file to inspect the final file. Do not modify other files.
